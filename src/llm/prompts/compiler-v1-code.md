- **code** runs a real script and draws its code and/or output ON the canvas — `{"id": "sim", "type": "code", "language": "python", "show": "left", "code": "import numpy as np\nrng = np.random.default_rng(7)\nx = rng.normal(size=200)\nprint(round(x.mean(), 3))"}`. The script EXECUTES in the viewer's browser at figure-preparation time, so treat it as load-bearing: keep it short (≤ ~14 lines), SEED any randomness, print() exactly the numbers the narration mentions, and end with at most ONE plot per stage — matplotlib ASSIGNED TO `_` (`_ = plt.hist(x, bins=20)`) so its return value's own repr does not flood the output panel with rows of array text, or plotly express LEFT IN A VARIABLE (`fig = px.bar(...)` — and IMPORT numpy and pandas alongside it, so the runtime preloads what plotly quietly needs; it renders as a static chart — and the `_ =` rule applies to ANY trailing call that returns the figure, `_ = fig.update_layout(...)` included). pandas works too — LEAVE a DataFrame as the LAST line (a bare `df` or `df.sort_values(...)`, NOT printed) and it draws as a clean ruled table with headers; use good column names since they become the header row. Packages auto-install: the scientific set ships with the runtime, and pure-Python PyPI packages (plotly, say) install on demand. Each code line is its own drawable `<id>_line_1` … `<id>_line_N` and the output panel is `<id>_out` — and `"marks"` puts a marker pen over the script: each entry is a VERBATIM piece of a drawn line (a whole line, or just the phrase you are about to explain) and becomes its own beat `<id>_mark_1`, `<id>_mark_2`, …, so `{"draw": ["sim_mark_2"], "speak": "…and this is the seed that makes it repeatable."}` sweeps a highlighter across exactly those characters while the sentence lands; `{"text": "…", "kind": "strike"}` crosses out instead. `"game"` puts a COMMODORE 64 PROGRAM on the machine — a KEY from drawcast's catalogue — `"c64maze"` (a 3D maze), `"crowboy"` (a side-scrolling beat-em-up demo), `"space-shooter"`, `"tenlander"` (a lunar lander in ten lines of BASIC), `"wolfling"` (a small platformer), `"invaders"` (space invaders), `"puralax"` (a colour puzzle), `"c-rex"` (Chrome's dinosaur runner), `"ronino"` (a board game against the computer), `"3d-cube"` (a wireframe cube to rotate), `"panopticon"` (a demoscene demo to watch), `"diffusion"` (particles diffusing, a tiny simulation), `"nono-pixie"` (a nonogram puzzle cartridge), `"space-orbs"` (a co-op puzzle cartridge); the schema carries their notes — or an https URL only when the user's request supplied one, never invented — paired with `"frame": "c64"` (or `"crt"`): the drawn screen shows the C64's blue boot screen with a play mark, a paused click starts it in a real emulator over the figure with sound and joystick, and `{"explore": {"game": "c64"}, "speak": "Now you play."}` is the beat that hands the viewer the joystick and waits (app only — a movie shows the drawn screen). `"chart"` picks how a matplotlib figure LOOKS — `seaborn` (the default: a calm grid in the figure's own colours), `xkcd` (hand-drawn wobble, which suits a sketched lecture), `plain` — and needs `language: "python"` — the signature move is stepping: draw the element's OWN id together with the first line(s) on the first beat, so the panel and its frame arrive WITH the code instead of popping in late — `{"draw": ["sim", "sim_line_1", "sim_line_2"], "parallel": true, "speak": "First, two hundred random draws."}` — then step the remaining lines one (or a few related ones) per beat: `{"draw": ["sim_line_3"], "speak": "..."}`, finishing with `{"draw": ["sim_out"], "speak": "And the mean lands where theory says."}` when the result should land. `show` picks the layout: `"output"` (just the result — the default), `"left"` or `"right"` (the code pane on that side, 55 % of the width; give the element width ≥ 700), `"above"` or `"below"` (the code pane stacked over or under the output at full width — `"below"` puts the OUTPUT on top, the notebook shape, so a chart sits where a plot pane would and the script is typed underneath it; set `"lines"`, a window of 6–8 lines, on a long script so it scrolls as the beats step past it); The panel is drawn on bare paper by default; `"frame"` puts it on something: `"screen"` is a computer display — one rounded shell with a chin, no stand — for when the story is that this HAPPENED on a computer, `"crt"` is an old tube monitor (chunky shell, bulging glass, little buttons on its chin, on a short foot) for a period or a retro-computing story, `"c64"` stands that same tube on a home-computer keyboard — the 1982 desk, `"laptop"` sets the flat display over a keyboard deck (hinge, keys, trackpad), `"window"` gives a title bar with three dots, `"panel"` a plain light frame. The machines with a chin — `screen`, `crt`, `c64` — carry three switches that WORK while the app is paused: the round one blanks the picture, the two small ones hide the code and hide the output, so a viewer can keep just the half they want (every code panel offers the same choices in the ⊕ tray; only these three draw them). `"draw": {"mode": "type"}` types the lines at typing speed with a blinking cursor — use it when the story is "watch me write this", and add `"lines"` so the screen scrolls like an editor. **Ask the viewer to WRITE it**: an `ask` that names a code element hands them the keyboard — `{"ask": {"question": "Add the numbers 0 to 9 into total.", "code": "task", "expect": "total", "answer": "45", "right": "Forty-five — Gauss's trick, one line at a time.", "wrong": "Not yet — check where the range stops.", "retry": true}}` with an empty or stubbed panel drawn first (`{"id": "task", "type": "code", "language": "python", "show": "left", "frame": "screen", "code": "# your turn"}`). The panel's editor opens on it, the viewer runs their script and presses Check, and `expect` reads the answer back — `"stdout"` (what they printed; the default), a VARIABLE they must leave behind (`"total"`, `"df.mean"`), or `"figure"` with `"answer": "1"` for "now plot it". Ask for a value a script can hit exactly (an integer, or a number the question says to round to); everything else an ask has still applies — retry, required, store, right_goto/wrong_goto — and movies skip the question, so the `right` line must state the answer for a viewer who never types. A script on screen is ALWAYS editable while the app is paused (the ⊕ tray, or a click on the screen), so `{"explore": {"code": "sim"}, "speak": "Change the rate and run it yourself."}` is not what makes it interactive — write it right after the output beat when the lesson should STOP and hand the viewer the keyboard (app only — movies skip the beat), `"code"` (the script alone), `"none"` (nothing drawn — the script only feeds template params, see the data bullet below). A CHANGING chart — new parameters, or bars/points added stage by stage as the narration walks through them — is one script that calls `plt.figure()` once per stage (axes limits held FIXED across stages, or the swap reads as a jump instead of a change) and declares `"figures": K`: each stage becomes its own beat `<id>_fig_1` … `<id>_fig_K`, all sharing one frame, so `{"draw": ["sim_fig_2"], "speak": "Now raise the rate."}` replaces the previous stage in sync with the voice (erase the old one first only when you want its exit animated). `language` picks the runtime: `"language": "python"` (full CPython — numpy, pandas, matplotlib, plotly, PyPI packages on demand) or `"language": "r"` (R — base or tidyverse; `library()` auto-installs; EVERY top-level expression prints as at the console, so a bare `summary(m)` shows; leave a data frame — tibble or data.table included — as the LAST line and it draws as a ruled table; a base `plot()` or a ggplot left as the last line draws as a figure, and `"figures": K` works with one plot per stage; the same `{id.path}` tokens feed templates from an R variable, a data frame column or a named vector). Write R when the request asks for R or the field's idiom is R; otherwise Python — and for Python, `"language": "brython"` is the LIGHT tier: CPython syntax and standard library plus pandas, plotly.express, numpy, matplotlib, scipy.stats, statsmodels and seaborn emulations, loading in about a second instead of tens of megabytes, so PREFER it for any script that needs no heavy numerics (build a frame, compute lists for tokens, a plotly express chart, a matplotlib-style plot, an OLS from statsmodels) — two known gaps: no `dataclasses` and no `statistics` module (compute a mean or a spread with plain arithmetic, or use numpy/pandas); use `"language": "python"` only when the real numpy/scipy/matplotlib or a PyPI package is needed. Emit `"language": "micropython"` only when the request asks for it (the minimal tier: half a megabyte, pandas and plotly.express emulations, a partial standard library — and its dicts keep NO insertion order, so build ordered data as lists, never from `dict.values()`). `"language": "basic"` is Commodore 64 BASIC V2 in drawcast's own small interpreter, and the element IS the machine's blue screen (no frame needed): NUMBERED lines are a program — typed onto the screen line by line (`<id>_line_k`), then `<id>_out` is RUN and shows what it printed, READY. and the cursor; BARE lines (no numbers) are immediate mode, the machine's own conversation — each line is typed and answered right under it, so draw `<id>_line_1`, `<id>_out_1`, `<id>_line_2`, `<id>_out_2` … in turn (PRINT 2+2 → 4, POKE 53280,0 turns the border black, READY. each time). PRINT, variables, GOTO/GOSUB, IF/THEN, FOR/NEXT, POKE/PEEK to the screen (1024+), colour RAM (55296+), border (53280) and background (53281), CHR$(147) to clear; no arrays, DATA, INPUT, SYS or sound in this first cut, and the error names what is missing. `"language": "microdata"` is microdata.no's OWN command language, not Python — the real emulator runs it on SYNTHETIC Norwegian register data, so no real person is ever involved; choose it when the request is about microdata.no, about analysing Norwegian register data, or about teaching that language. Every script opens with the prologue `require no.ssb.fdb:54 as fd`, then `create-dataset <name>`, then one `import fd/<VARIABLE> [<date>] as <alias>` per variable — `<VARIABLE>` must be a REAL FDB name (BEFOLKNING_KJOENN, BEFOLKNING_FOEDSELS_AAR_MND, INNTEKT_WLONN, INNTEKT_SAMLET_SKATTEPL, BOSATTEFDT_BOSTED, NUDB_BU, SYKEFRAVAR_TAPTEDAGSVERK, …); an invented one is refused before the script runs, because the mock-data engine would otherwise fabricate a column for it and the lesson would teach a variable that does not exist. The verbs that TRANSFORM: `generate`/`replace` (expressions, `log()`, `sysmiss()`), `keep`/`drop` (bare or with `if`), `recode`, `destring`, `define-labels` + `assign-labels`, `collapse`, `merge`, `sample`; the ones that PRINT: `tabulate` (one or two variables), `summarize` (options like `gini iqr`, and `if`), `correlate`, `regress`/`logit`/`probit`/`poisson`; the ones that DRAW: `barchart`, `histogram`, `boxplot`, `scatter`, `piechart`. Never add `print` — a printing command draws ITSELF as a ruled table and a drawing command as a chart. Put at most ONE printing or drawing command in an element: tables stack under the text, so two of them lose their order — and one command per element is the teaching rhythm anyway, one beat per command. Comments are `//`. Two traps: a loop is `for y in 1998:2009` … `end` with NO parentheses and NO nesting (several levels go in one header, separated by `;`), and a missing value is `sysmiss(x)`, never `x == .`. `{id.df}` is the active dataset and `{id.<dataset>.<column>}` one of its columns, so `data_table`, `bar_chart` and the other data templates can be fed straight from a microdata script — but `collapse` FIRST: a dataset is ten thousand people, and the bridge refuses more than 5000 numbers or 200 rows, which is also the honest lesson (you never plot individuals, you aggregate them). One code element per figure. Never write `code_result` — the app fills it.
- **Data from code, drawn as ink.** A template param may name a code element's variable with a TOKEN: `"values": "{sim.y}"`, `"labels": "{sim.df.country}"` (a DataFrame column), `"data": "{sim.df}"` (a whole frame). The script runs once, the app substitutes the values, and the template draws them as vector geometry — so use `bar_chart` / `data_table` with a token INSTEAD of `plt.bar(...)` or a printed frame whenever the numbers come from computation; the chart then animates, scrubs and exports exactly, and costs bytes, not pixels. The same rules drive `line_chart` (`x` numbers or category strings, `values` or `series`, each line ends in its name — a shorter earlier stage reveals a line point by point) and `scatter_plot` (`x`, `y`, optional per-point `labels` that become `point_i` beats, and `fit: true` for a least-squares line or `fit: [slope, intercept]` from the script — the `points` beat draws every unnamed dot at once), `bar_race` (stages of one field whose rows REORDER as the numbers change — animate its `stage` the whole way with `"easing": "linear"`) and `heatmap` (a 2-D grid washed by density, one `row_k` beat per row). The two workhorses take a mode as well: `stacked: true` on `bar_chart` piles the series into one bar, `slope: true` on `line_chart` gives the two-column before/after with every line labelled at both ends. Rules: the variable must be a number, list, dict, Series or DataFrame (`frames = [df.y2010.tolist(), df.y2020.tolist()]`); **Depth means staged** — a list of lists is stages of the SAME chart, and `{"animate": {"stage": 1}}` plays the change; ALWAYS write the starting `"stage": 0`; **TYPE the labels by hand** even when values come from the script, so the `bar_1` … `bar_n` beats exist before it has run; a script that only feeds data gets `"show": "none"` (nothing drawn — no line beats, no output pane), one that is part of the story gets `"show": "code"` — and the app then SPLITS the canvas by itself, script on the left and chart on the right, so write neither the code element's `x`/`width` nor the template's `box` unless you mean to override that. Example: `{"template": "bar_chart", "params": {"labels": ["Norway", "Sweden", "Denmark"], "values": "{gdp.frames}", "stage": 0, "title": "GDP per capita, 2010 → 2020"}, "elements": [{"id": "gdp", "type": "code", "language": "brython", "show": "none", "code": "import pandas as pd\ndf = pd.DataFrame({\"c\": [\"Norway\", \"Sweden\", \"Denmark\"], \"y2010\": [87, 52, 58], \"y2020\": [67, 52, 61]})\nframes = [df.y2010.tolist(), df.y2020.tolist()]"}], "commands": [{"draw": ["axes", "bar_1", "bar_2", "bar_3"], "speak": "In 2010 Norway towered over its neighbours."}, {"animate": {"stage": 1}, "duration": 3, "speak": "Ten years on, the oil price took the tower down."}]}`. Never put a token inside a longer string, and never reference an element that is not a code element. **Tokens are not limited to the data pack**: any template whose description says it accepts `"{id.var}"` takes them in the params that description names — `forest_plot` (study and pooled estimates), `survival_curve` (each arm's `survival` list), `distribution_curve` (the shade boundary), `ceac` (a strategy's `midpoint`), `did_trends` and `event_study` (the estimated `effect`) — so a computed result can drive a clinical or economic figure, not just a bar chart. Each of them keeps its typed companions (study names, arm labels, group names) so the beats exist before the script has run.
