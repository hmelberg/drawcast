# Design: Revise with AI, and history as the document lifecycle

*2026-08-24. Decisions made in brainstorming with Hans, grounded in a read of the
existing generate path (`src/main.ts` `generate()` → `src/llm/compile.ts`
`generateSpec()` → `setDoc()`), the playlist format (`src/playlist/playlist.ts`),
and the library (`src/store.ts` §"Drawing library").*

## Goals

1. **Revise** an existing drawcast by describing a change, instead of regenerating
   it from scratch. One button, next to Generate, using the document you can see.
2. **Saving disappears.** Everything you make is kept automatically, with a
   per-document version history you can walk back through — across reloads.
3. **One primary action at a time.** Generate when nothing of yours is on screen,
   Revise when the document is the thing you are working on.
4. **Nothing is ever silently destroyed.** No confirm dialogs, because there is no
   destructive moment to confirm.

## Non-goals (v1)

- **Branching version trees.** Restore and revise-from-old both *append*; each
  document has one linear log.
- **Per-part revision of playlists.** Whole document in, whole document out (§2).
- **`#tags` and the template picker on revise instructions.** The instruction is
  passed through as written; model and active prompt variant still apply.
- **A diff view between versions.** The arrows re-render the figure; comparing two
  versions side by side is a later feature.
- **Cloud sync.** History is localStorage, this browser — same as the library it
  replaces.

## 0. Phasing — what is actually being built

Evaluated 2026-08-24 with Hans, after the design was complete: the two halves of
this spec have very different returns, so only the first is being built now.

**Phase 1 — build now.** Revise (§2), an in-memory session version stack (§4),
and auto-save in place. Purely additive: a Revise bug returns a bad spec, and
nothing that works today changes shape. Small enough to be worth doing on
speculation.

**Phase 2 — deferred.** Persisted versions, the storage split, eviction,
migration, star, rename, and the three-origin state machine (§1, §3, §5). This is
*library management*, and it earns out only if drawcasts accumulate into a corpus
that gets re-opened. That fact does not exist yet — drawcast is five days past the
fork and still in heavy feature development. It is also the only subtractive part
of the spec: it replaces a working persistence layer and migrates real saved data,
where a bug loses work.

**The trigger.** Build phase 2 when the sidebar has become a list that actually
gets scrolled and re-opened. Until then, undo-for-revise — the thing phase 2 was
originally justified by — costs ~120 lines of in-memory stack instead of a
persistence rewrite.

Building storage twice is normally an argument against phasing, but not here: the
standing rule for this repo is no backwards compatibility while there are no users
(replace and delete rather than migrate), which already prices the second pass as
cheap.

### Phase 1 substitutions

| spec section | phase 2 as designed | phase 1 instead |
|---|---|---|
| §1 origins | `demo`/`opened`/`owned`, boot offers Generate | unchanged boot (`initialDoc`); **Generate always present, Revise appears whenever a document is loaded**; arrows hidden until there are ≥2 versions |
| §3 storage | index + per-entry version blobs, caps, eviction, migration | **no `store.ts` change at all** — `Doc` gains a stable `id`, and `saveDrawing` already replaces by id (`store.ts:188`), so passing it auto-saves in place |
| §3 persistence | 10 versions per entry, on disk | current version only; the version stack is in memory, capped at 20, gone on reload |
| §5 sidebar | History panel, rename, star, hover actions | unchanged Library panel; `💾 Save` is removed as redundant |

Copy-on-write still applies in phase 1: Generate creates a library entry
immediately, a loaded example or `#gdoc=` share creates nothing until the first
revise or manual re-render. Auto-save fires on generate, revise **and** manual
re-render, which is what makes `💾 Save` redundant.

## 1. Three origins, two buttons *(phase 2)*

`Doc` gains `origin` and `entryId`. The primary button follows **how the document
arrived**, not what is on screen:

| origin | how you got there | `entryId` | primary button | arrows |
|---|---|---|---|---|
| `demo` | boot example; sidebar ▸ New (`BLANK_SPEC`) | `null` | **Generate with AI** | hidden |
| `opened` | a bundled example you clicked; a `#gdoc=` share | `null` | **Revise with AI** | hidden |
| `owned` | generated by you; opened from History | set | **Revise with AI** | when >1 version |

The reasoning: anything drawcast put in front of you is a demonstration, so the
next thing you do is start your own. Anything you actively chose is what you are
working on.

**This removes the empty state entirely.** Boot shows a bundled example and New
shows `BLANK_SPEC` — both `demo`, both offering Generate — so the player never
boots into a grey box and there is no blank screen to design.

**Copy-on-write.** Any change to a non-`owned` document (a revise, or a manual
re-render) creates a history entry and flips origin to `owned`. Merely *loading*
an example or a share creates nothing. Hand-editing the boot example therefore
forks it into your history, which is the same rule that forks a revised example.

Generate is unreachable while a document is `opened` or `owned`. New is the way
back to it — one click, deliberately.

## 2. The revise call *(phase 1)*

New module `src/llm/revise.ts`, sitting beside `compile.ts` the way `author.ts`
and `outline.ts` already do, importing `repairModelFor`/`needsRepair` from it.

**Whole document, text in → text out.** A multi-part drawcast is already a
multi-document YAML stream (`---` on its own line, `{playlist: {…}}` header,
`{chapter: …}` markers, everything else a spec item — `playlist.ts:59-104`), the
editor textarea already holds exactly that (`formatPlaylist`), and
`parsePlaylistText` already reads any of it back. So single spec and playlist are
one code path with no wrapper schema, and the model can add, drop, reorder and
retitle parts — which per-part revision cannot.

- **System blocks: the active compiler variant, unchanged.** The same
  `buildSystemBlocks(...)` with the same `cache_control` prefix as generation, so a
  Revise following a Generate reuses the warm ~10k-token cached prefix.
- **Catalog priority.** Every `template:` id present in the current document is
  passed as `priorityIds` to `catalogParts`, so the model receives those templates'
  **full** catalog entries rather than one-line index stubs — it cannot revise
  params it cannot see. The instruction drives the keyword shortlist.
- **User message**, built by a pure `buildReviseUser(docText, instruction)`: the
  current document in a fence, the instruction, and an explicit *"return the
  COMPLETE document in the same format; change only what the instruction asks
  for."*
- **Response**: `callForText` → `stripFence` → `parsePlaylistText` →
  `validateSpec` **and** `layoutSpec` on every item → the capped repair loop
  (`maxRepairs: 2`, repairs on `repairModelFor(model)`). Repair feedback names the
  offending item: *"item 3 failed validation: …"*.
- **Input is the textarea, not `doc`** — so unsaved hand-edits ride along into the
  revision. That is deliberate; §3 keeps the resulting label honest about it.

Structured output is not used. `callForJson` constrains output to the single-`Spec`
schema, and that schema declares `params: {additionalProperties: true}`
(`spec/schema.ts:251`) — precisely the open-params case `client.ts:76-78` records
the structured-output grammar as rejecting, after which `featureBroken.structuredOutput`
makes generation fall back to `extractJson` text parsing anyway.

**Size is not a constraint.** Median bundled spec is 1.2 kB of JSON (≈330 tokens),
largest 2.5 kB (≈715). A five-part playlist round-trips in ≈1.7–3.6k output tokens
against `max_tokens: 16000` (`client.ts:54`). Roughly 15–20 parts before it bites;
a document that large fails loudly on `max_tokens`, not silently.

```ts
export interface ReviseConfig {
  apiKey: string;
  model: string;
  variant: PromptVariant;        // the active compiler prompt, as generation uses
  priorityIds?: string[];        // templates present in the document, + priority packs
  maxRepairs?: number;           // default 2
}
export interface ReviseOutcome {
  playlist: Playlist | null;
  text: string | null;           // the accepted document text, as returned
  rounds: ReviseRound[];
  error?: string;
}
export function reviseDocument(docText: string, instruction: string, cfg: ReviseConfig): Promise<ReviseOutcome>;
```

Exemplars are deliberately absent from `ReviseConfig`: `pickExemplars` selects
worked *request → spec* pairs, which teach initial authoring. A revision already
has a spec in front of it, so the slots would spend cached prefix on examples of a
task the model is not doing.

### Logging and ratings

`logOutcome` takes a `GenerationOutcome` and a single `spec`, so it gains a
sibling for revisions rather than being contorted: one `LogEntry` per revise,
`prompt` recorded as `` `${entry.prompt} ⟶ revise: ${instruction}` `` (mirroring how
`generateMulti` labels part logs), `spec` the first item. `lastLogId` is set after
the document is applied, exactly as `generate()` does, so the rating stars target
the revision you just made.

## 3. Versions and storage *(§3 storage shapes are phase 2; the version rules below apply to both phases)*

Two localStorage shapes, replacing `KEYS.library`:

```ts
// drawcast.history.v1 — the index. ~150 bytes/row; rewritten on every action.
interface HistoryEntry {
  id: string;
  title: string;
  starred: boolean;
  prompt?: string;        // the ORIGINAL request; never overwritten by revisions
  ts: string;             // last modified
  versionCount: number;   // so the sidebar can hint without loading the stack
}

// drawcast.versions.v1.<id> — one blob per entry; only the touched entry is rewritten.
interface VersionStack { versions: Version[] }        // newest last, max 10
interface Version {
  text: string;                                  // the serialized document (formatPlaylist output)
  label: string;
  kind: "generate" | "revise" | "manual" | "restore";
  from?: string;                                 // parent's LABEL when derived from a non-newest version
  ts: string;
}
```

Splitting the index from the stacks is what makes auto-save affordable: the
sidebar renders from ~30 kB no matter how much drawing text you own, one revise
rewrites ~15 kB instead of the whole library, and evicting an entry is one
`removeItem`. It does not raise the ~5 MB origin ceiling — it stops us reaching it
an order of magnitude sooner.

`text` is stored, not a parsed playlist: it is what the editor shows, what Revise
sends, and what `parsePlaylistText` reads back, so nothing re-serializes and
nothing drifts.

`prompt` stays the original request for the life of the entry, so exemplars, the
log and "👍 Learn from this" keep pairing *original request → current spec*.

**There is no persisted `pos`.** Opening an entry always shows its newest version;
the view cursor (§4) is in-memory only.

### When a version is pushed

| action | effect |
|---|---|
| Generate | new entry; version `generate`, label = the request; title from `spec.title ?? request` |
| Revise | push `revise`, label = the instruction |
| Re-render (manual) | if the newest version is already `kind: "manual"` **and** the cursor is on it → **update it in place**, refresh `ts`. Otherwise push `manual`. |
| Revise with a dirty textarea | label gets `" (+ manual edits)"` — the hand-edits ride along, so the label must not lie |
| Restore (§4) | push `restore`, label `restored "<parent label>"` |
| Revise or Restore from a non-newest cursor | push as normal, and set `from` = the parent version's label |

A `manual` push can never come from a non-newest cursor: Re-render is disabled
while viewing (§4), so hand-edits only ever land on the newest version.

Every push moves the view cursor to the newest version — after a revise you are
looking at what you just asked for, not at where you were browsing.

Coalescing is the answer to manual edits flooding the stack: a run of re-renders
collapses into one `manual` version whose timestamp refreshes, and the next AI
action seals it. `from` references the parent's **label**, never a number, so it
does not go stale when the 10-cap drops old versions.

### Caps and eviction

- **10 versions per entry.** Pushing the 11th drops the oldest.
- **100 unstarred entries.** Creating the 101st drops the oldest unstarred entry —
  index row and version blob together.
- **On `QuotaExceededError`**: drop the oldest unstarred entry and retry, up to 5
  times, then surface an error via `setStatus`. This mirrors `appendLog`'s
  halving-on-quota strategy (`store.ts:322-325`).
- **Starred entries are never evicted by any rule.** That is what starring *does*,
  beyond sorting first.

### Migration

One-shot, guarded by a marker key in the style of `KEYS.packsUpgrade`: each
existing `SavedDrawing` becomes a `HistoryEntry` plus a `VersionStack` holding one
`generate` version whose `text` is `playlist ?? formatSpec(spec, "yaml")`. The old
`drawcast.library.v1` key is then removed. Hans has his own saved drawings in this
browser; they must survive.

## 4. Viewing versus restoring *(phase 1, over the in-memory stack)*

**The arrows navigate. A button commits. Neither deletes.**

Stepping back is pure viewing: the figure re-renders, the spec pane goes
read-only, Re-render is disabled, and a bar names what you are looking at.

```
at the newest version:
  ◀ 5/5 ▶                                   [ Revise with AI ]

stepped back to the 2nd:
┌──────────────────────────────────────────────────────────────┐
│ ◀ 2/5 ▶   Viewing an older version                           │
│           [ Restore ]              [ Latest ▸ ]              │
└──────────────────────────────────────────────────────────────┘
  spec pane read-only                       [ Revise from here ]
```

**Restore appends a copy** of the viewed version as the newest one — it does not
rewind into it. **Revise from an older version also appends**, recording `from`.
So no version is ever removed by a user action, there is no redo tail to truncate,
and there is nothing to confirm. The only thing that removes a version is the
age-based 10-cap, which is predictable.

The counter shows position among stored versions (`2/5`); the counter's `title`
shows that version's label and timestamp.

## 5. The sidebar: History *(phase 2)*

"Library" becomes **History**. Rows sort starred-first then newest; the existing
search filter (`matchesFilter`) is unchanged. Actions appear on hover:

```
 ★ Supply and demand shift                        ✎  ★  ✕
   Decision tree, two branches                    ✎  ☆  ✕
```

`✎` renames inline, `★`/`☆` toggles starred, `✕` deletes the entry and its version
blob. `💾 Save` is removed — saving is automatic. Export/import stay as they are.

`main.ts` is 2503 lines, so when phase 2 lands the sidebar panel moves **out**
rather than in — the same split `src/ui/controls.ts` and `src/ui/modal.ts`
already use.

**Implementation trap:** `doc` is assigned in two places, not one — `setDoc()`
(`main.ts:1389`) and the `rerenderBtn` handler (`main.ts:1733`), which writes
`doc = {…}` directly. A version push hooked only into `setDoc` silently misses
every manual edit.

## 8. Known limits, accepted

- Generate is unreachable without pressing New first. Deliberate — it is the
  mechanism that makes "the document on screen is what you are working on" true.
- A revise that also carries hand-edits is one version, labelled
  `"… (+ manual edits)"`. Splitting it into two versions would require diffing the
  textarea against the stored text on every keystroke.
- The 10-version cap can drop the version a `from` label names. The label is human
  text, not a link, so it degrades to a description rather than breaking.
